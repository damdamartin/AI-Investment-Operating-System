## Purpose

This document tells the human **project owner** and the human **risk
owner/operator** exactly what evidence they must personally gather and
record before `LCB-004` (Human Approval Evidence) and `LCB-006`
(Small-Capital Operating-Limit Evidence) in
`docs/phase7/live-capable-blocker-register.md` can even be considered by a
human reviewer.

This document does not resolve `LCB-004` or `LCB-006`. It does not
authorize live trading. It does not invent, suggest, or approve any risk
limit on the human operator's behalf. The only place either blocker can
ever be marked `RESOLVED` is `docs/phase7/live-capable-blocker-register.md`
itself, edited directly by a human reviewer recording a reviewer name,
reviewed date, and decision -- never by this document, never by the
optional pure evaluator described below, and never by any AI agent.

## What A Human Must Personally Do Before Using This Packet

1. Personally read `docs/phase7/live-capable-blocker-register.md`'s
   `LCB-004` and `LCB-006` entries in full.
2. Personally read `docs/phase7/manual-live-approval-record.md` (why an
   approval cannot be inferred, guessed, defaulted, or generated by AI
   output) and `docs/phase7/small-capital-readiness-gates.md` section 1
   (numeric capital limit categories) and section 11 (rollback procedure).
3. Personally decide the actual numeric limits for this packet's capital
   policy fields. Nothing in this document, and nothing in the optional
   evaluator, supplies, recommends, or defaults a number. The illustrative
   figures in `docs/phase7/small-capital-readiness-gates.md` section 1 are
   explicitly "not hardcoded anywhere as 'the' limits" -- an operator must
   independently choose and record their own values here.
4. Personally decide whether to approve, reject, or mark unverified, using
   only the five decision values in "Allowed Decision Values" below.

## Sanitization Rules (Restated From The Workbook)

This packet, and any evidence intake built on top of it, must never
contain:

- API keys, client secrets, tokens, passwords, certificate material
- account numbers, raw broker payloads, raw HTTP headers
- local receipt contents (`tmp/phase5/**`) or `.env` contents
- balances, holdings quantities, or personally identifying contract text
- real account values of any kind, even in examples -- every numeric
  example in this document uses a synthetic, clearly-labeled placeholder
  value, never a real account figure

A declared capital policy limit (see "Required Fields" below) is a
**policy ceiling**, not a balance or holdings quantity, and is the one kind
of number this packet is designed to carry -- but it must still never be
tied to an identifiable real account.

## Allowed Decision Values

Use only these five values, per
`docs/phase10/human-blocker-evidence-workbook.md`:

```text
READY_FOR_HUMAN_REVIEW
HUMAN_REVIEWED_APPROVED_WITH_LIMITATIONS
HUMAN_REVIEWED_REJECTED
HUMAN_REVIEWED_UNVERIFIED
NEEDS_MORE_EVIDENCE
```

`RESOLVED` must never be used anywhere in this packet, in any document
derived from it, or in any evaluator output. `RESOLVED` belongs
exclusively to a human editing
`docs/phase7/live-capable-blocker-register.md` directly.

## Required Fields

Every owner/risk evidence packet instance must record all of the
following. A missing field is always a blocking gap, never an implicit
"assume fine."

| Field | What it records |
| --- | --- |
| Packet id | Stable identifier for this packet instance. |
| Covered blocker ids | Always exactly `LCB-004`, `LCB-006`. |
| Evidence source references | Sanitized citations to where the underlying evidence lives (doc paths, dated notes) -- never secrets, account numbers, or raw payloads. |
| Human reviewer name | The actual human who reviewed this packet, typed by them. Never "AI", "Claude", "Codex", or any automated-system identity. |
| Human reviewer role | The reviewer's actual human role (for example "Project owner", "Risk owner/operator"). Never "AI" or "System". |
| Review date | The date the human reviewer actually performed this review. Never in the future. |
| Decision/result | One of the five allowed decision values above. |
| Limitations or restrictions | What this packet's evidence does and does not cover. Never blank -- write "None identified" if genuinely none, but never omit the field. |
| Expiration or next review date | When this packet must next be revisited. Must be after the review date, per the same periodic-re-attestation discipline `docs/phase7/manual-live-approval-record.md` establishes for `ManualLiveApprovalRecord.expiresAt`. |
| Prohibited-content confirmation | Explicit confirmation from whoever prepared the packet that they personally checked it against the sanitization rules above, in addition to any automated scan. |
| Not-live-trading-authorization statement | A fixed, explicit statement (reproduced below) that this packet is not, and can never become, live-trading authorization. |

## The Nine Checklist Topics

These map directly to the P10-007 task's required output list. Each topic
needs a genuine, personally-typed human attestation -- a boolean flag alone
proves nothing, so each topic below has a required verbatim statement (see
`REQUIRED_OWNER_RISK_ATTESTATIONS` in the optional evaluator, or write the
equivalent by hand if not using the evaluator) that the attesting human
must type themselves, along with their own name, role, and the date.

### 1. Explicit Human Approval Intent (`LCB-004`)

The project owner records that they personally, explicitly intend to
approve progression from readiness evidence toward a later, separately
reviewed live-implementation phase. This is intent, not the final
decision -- the final decision is the packet's own "Decision/result" field,
recorded separately once review is actually complete.

### 2. Residual-Risk Acknowledgment (`LCB-004`)

The project owner acknowledges that a future small-capital live pilot
carries residual risk -- including risk of loss of the declared capital --
that no amount of testing, review, or automation can fully eliminate, and
personally accepts that risk.

### 3. Maximum Total Capital Policy (`LCB-006`)

The risk owner/operator personally declares a strict maximum total capital
exposure ceiling for the pilot -- a `Money` value (amount + currency), per
`docs/11_AI_RULES.md` Rule 20, never a naked number. This packet never
supplies, suggests, or defaults this value. Example placeholder only, not a
recommendation:

```text
declaredValue: { amountMajor: "3000000", currency: "KRW" }   // SYNTHETIC EXAMPLE ONLY
```

### 4. Maximum Per-Order Policy (`LCB-006`)

The risk owner/operator personally declares a strict maximum per-order
amount ceiling, in the same `Money` shape as above. Same "never
supplied/suggested/defaulted" rule applies.

### 5. Allowed Strategy Set (`LCB-006`)

The risk owner/operator personally lists a limited, explicit set of
strategy identifiers this pilot may run (matching
`docs/07_Trading_System.md` section 30's "limited number of strategies").
Never a symbol, quantity, side, or price -- strategy identifiers only.

### 6. Limit-Order-Only Restriction (`LCB-006`)

The risk owner/operator confirms every order in this pilot will use limit
orders only, per `docs/07_Trading_System.md` section 25.

### 7. Regular-Hours-Only Restriction (`LCB-006`)

The risk owner/operator confirms every order will be placed only within
the regular trading session for its market -- no extended-hours or
fractional orders, per `docs/07_Trading_System.md` section 25 and
`docs/phase7/small-capital-readiness-gates.md` section 2.

### 8. Daily Review Commitment (`LCB-006`)

The risk owner/operator commits to personally performing a daily
reconciliation and risk review of the pilot's activity, and records a
short description of how that review will actually happen. Never
delegable to an automated process.

### 9. Stop Criteria (`LCB-006`)

The risk owner/operator confirms explicit stop criteria exist that halt
trading for human review when triggered (for example, any declared limit
being breached), and records a short description of what triggers a stop
and how the resume decision will be made.

## How The Capital Policy Fields Separate "Proposed" From "Human-Approved"

This is the single most important structural property of this packet, and
the optional evaluator enforces it directly:

- The **declared value** for `maxTotalCapitalPolicy` and
  `maxPerOrderPolicy` is always exactly what the human owner/risk reviewer
  personally typed in. Nothing in this document or the optional evaluator
  computes, suggests, or defaults that number.
- Whether that declared value counts as **approved** is a completely
  separate question, answered *only* by the packet's own
  "Decision/result" field once a human reviewer has actually completed
  review -- never inferred from the number itself, never inferred from the
  mere presence of a value, and never inferred from a clean-looking
  packet.
- A declared value with no completed human review reads as **proposed,
  pending human decision** -- not approved, not rejected, just proposed.
  It stays in that state until a human reviewer records
  `HUMAN_REVIEWED_APPROVED_WITH_LIMITATIONS`,
  `HUMAN_REVIEWED_REJECTED`, or `HUMAN_REVIEWED_UNVERIFIED`, together with
  every other required reviewer field and a verbatim reviewer attestation
  (see below).
- If the review decision claims approval but any required reviewer field
  is missing, invalid, or the attestation does not match verbatim, the
  capital policy fields remain **proposed, pending human decision** -- they
  are never silently upgraded to an approved state.

## Why This Cannot Be Faked By AI-Generated Text

Mirroring the same structural discipline established by
`docs/phase7/manual-live-approval-record.md` and
`docs/phase10/first-trade-operating-protocol.md`:

- Every identity-bearing field (attester names, attester roles, the human
  reviewer's name and role) is checked against text that claims to be an
  AI, an automated system, or a named AI product. A match blocks the
  field. This never proves a human actually performed the review, but it
  structurally blocks the most obvious way an AI-generated approval could
  be passed off as a human's own sign-off.
- Every attestation-bearing topic requires a fixed, exact, per-topic
  statement typed verbatim -- not a paraphrase, not a summary, not a
  boolean flag alone.
- A completed human review (any `HUMAN_REVIEWED_*` decision) additionally
  requires a distinct, verbatim reviewer-level attestation that itself
  states the packet does not resolve either covered blocker.
- If an AI coding agent, or any other automated process, is ever asked to
  "just fill in the approval," "mark this as approved," or "pick reasonable
  limits so the gate passes," that instruction violates
  `docs/11_AI_RULES.md` Rule 12 ("AI may propose strategy changes, not
  apply them directly") and Rule 22 ("fail closed"), and must be refused --
  the safe alternative is to ask the actual human owner/risk reviewer to
  fill in and sign the packet themselves.

## Optional Pure Evaluator

`src/application/live-readiness/owner-risk-evidence-packet.ts` exports
`evaluateOwnerRiskEvidencePacket`, a pure, side-effect-free function that
checks a caller-supplied packet instance for **structural completeness
only**: are all required fields present, sanitized, and internally
consistent. It never computes, proposes, or auto-fills a risk-limit
number, it never produces an executable order shape (no field anywhere
combines a symbol/asset identifier, a quantity, a side, and a price), and
`liveBrokerWriteAllowed` is a hardcoded literal `false` on every report,
never derived from any input.

`packetEvidenceComplete: true` from this evaluator means the packet is
filled in correctly -- it does **not** mean the recorded decision is
favorable, and it never means `LCB-004` or `LCB-006` is resolved. A packet
with a `HUMAN_REVIEWED_REJECTED` decision and every other field valid also
reads `packetEvidenceComplete: true`.

Tests: `tests/application/owner-risk-evidence-packet.test.ts`.
