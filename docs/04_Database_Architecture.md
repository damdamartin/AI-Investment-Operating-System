## 1. Document Purpose

This document defines the database architecture for AI Investment Operating System.

It describes persistence principles, schema groups, key tables, audit rules, historical data strategy, indexing, retention, backup, and recovery requirements.

This document is not a final migration file. Exact SQL migrations will be created during implementation, but they must follow this architecture.

## 2. Database Goals

The database must support four critical goals:

1. safe trading
2. full auditability
3. reproducible strategy validation
4. long-term learning and analysis

The database must allow the system to answer:

- What did the system know at the time?
- Which strategy version generated the signal?
- Which engine scores contributed to the decision?
- Which AI analysis was used, if any?
- Which risk limits passed or failed?
- Why was an order approved or rejected?
- What did the broker return?
- What was actually filled?
- How did the position and cash balance change?
- Which strategy version performed better over time?

If the database cannot reconstruct why a production order happened, the design is incomplete.

## 3. Recommended Database Choice

Initial recommendation:

```text
PostgreSQL
```

Reasons:

- strong transactional consistency
- mature indexing
- JSONB support for flexible external API payloads
- good time-series partitioning options
- reliable audit and history patterns
- broad cloud hosting support
- strong migration tooling ecosystem

Optional future additions:

- object storage for raw large payloads
- Redis for short-lived cache and job locks
- queue system for asynchronous workflows
- analytics warehouse if historical data becomes large

The canonical source of truth for production trading state must remain the transactional database.

## 4. Persistence Principles

### 4.1 Never Store Money Without Currency

Every money field must include currency either as a separate column or through a constrained composite model.

Bad:

```text
amount = 10000
```

Good:

```text
amount = 10000
currency = KRW
```

### 4.2 Separate External IDs From Internal IDs

Internal IDs must be generated by the system.

External IDs from Toss Securities, Naver, or Claude must be stored as external reference fields.

This prevents external API format changes from breaking domain identity.

### 4.3 Append-Only for Critical Facts

The following data should be append-only:

- audit records
- domain events
- strategy version approvals
- order approvals
- broker order responses
- fills
- AI analysis outputs
- risk check results
- health check results

If correction is needed, create a correction record instead of rewriting history.

### 4.4 Immutable Strategy Versions

Once a strategy version is approved for any validation or trading stage, it must not be edited in place.

Changes require a new `strategy_versions` row.

### 4.5 Store Raw and Normalized External Data Separately

External API responses should be stored or referenced for audit, but normalized tables should drive domain behavior.

Pattern:

```text
raw_external_payloads
-> normalized domain tables
```

### 4.6 Use Conservative Defaults

Missing or uncertain data should lead to blocked trading, not inferred values.

Database nullable fields must be intentional. Required trading data should be `NOT NULL` where practical.

## 7. Core Tables

### 7.1 `assets`

Purpose:

Stores normalized internal asset records.

Key columns:

| Column | Type | Notes |
|---|---|---|
| id | uuid | primary key |
| market_code | text | `KR` or `US` |
| asset_type | text | `STOCK` or `ETF` |
| symbol | text | normalized internal symbol |
| display_name | text | human-readable name |
| currency | text | `KRW` or `USD` |
| exchange | text | exchange code |
| tradability_status | text | tradability state |
| data_status | text | data quality state |
| created_at | timestamptz | creation time |
| updated_at | timestamptz | update time |

Constraints:

- unique `(market_code, asset_type, symbol)`
- currency must match market rules unless explicitly allowed
- tradability status must be an allowed enum value

### 7.2 `broker_asset_mappings`

Purpose:

Maps internal assets to Toss Securities API identifiers.

Key columns:

| Column | Type | Notes |
|---|---|---|
| id | uuid | primary key |
| asset_id | uuid | references `assets.id` |
| broker | text | initially `TOSS_SECURITIES` |
| broker_symbol | text | Toss-specific symbol |
| broker_market_code | text | Toss-specific market code |
| broker_asset_type | text | Toss-specific asset type |
| orderable | boolean | true only if verified |
| supports_fractional_quantity | boolean | nullable until verified |
| supports_market_order | boolean | nullable until verified |
| supports_limit_order | boolean | nullable until verified |
| verified_at | timestamptz | verification time |

Constraints:

- unique `(broker, broker_symbol, broker_market_code)`
- production order requires `orderable = true`

### 7.3 `market_calendars`

Purpose:

Stores trading days and sessions by market.

Key columns:

| Column | Type | Notes |
|---|---|---|
| id | uuid | primary key |
| market_code | text | `KR` or `US` |
| calendar_date | date | market-local date |
| is_open | boolean | open or closed |
| session_type | text | regular, pre-market, after-hours |
| open_at | timestamptz | session open |
| close_at | timestamptz | session close |
| reason_if_closed | text | holiday or closure reason |
| source | text | source of calendar data |

Constraints:

- unique `(market_code, calendar_date, session_type)`

- `news_events` influence signals but do not directly approve orders.

|---|---|---|

## 18. Index Strategy

General index principles:

- Index foreign keys used in joins.
- Index timestamp columns used in recent-history queries.
- Index status columns only when selectivity and query patterns justify it.
- Use composite indexes for common access patterns.
- Avoid excessive JSONB indexes until query patterns are proven.

Critical indexes:

- `assets(market_code, asset_type, symbol)`
- `broker_asset_mappings(broker, broker_symbol, broker_market_code)`
- `market_data_snapshots(asset_id, captured_at desc)`
- `signals(strategy_version_id, generated_at desc)`
- `order_intents(signal_id)`
- `order_approvals(order_intent_id)`
- `broker_orders(broker, broker_order_id)`
- `broker_orders(order_state, submitted_at desc)`
- `fills(broker_order_id)`
- `positions(portfolio_id, asset_id)`
- `portfolio_snapshots(portfolio_id, captured_at desc)`
- `risk_checks(subject_type, subject_id)`
- `domain_events(aggregate_type, aggregate_id, occurred_at)`
- `audit_records(subject_type, subject_id, created_at)`

## 19. Partition Strategy

Partition only when data volume justifies it. Premature partitioning can add complexity.

Likely partition candidates:

- `market_data_snapshots` by month on `captured_at`
- `portfolio_snapshots` by month or quarter on `captured_at`
- `domain_events` by month on `occurred_at`
- `audit_records` by quarter or year on `created_at`
- `api_call_logs` by month on `called_at`

Tables that should usually not be partitioned initially:

- `assets`
- `broker_asset_mappings`
- `strategies`
- `strategy_versions`
- `risk_limits`
- `portfolios`

## 20. Data Retention Policy

Retention should balance auditability, cost, and usefulness.

Suggested initial retention:

| Data | Retention |
|---|---|
| Production orders and fills | permanent |
| Strategy versions and promotion reviews | permanent |
| Audit records | permanent or long-term archive |
| Domain events | long-term archive |
| Portfolio snapshots | long-term, downsample optional |
| Market data snapshots | detailed for active period, archived later |
| Raw news articles | 1-3 years initially |
| Raw external payloads | based on audit relevance |
| API call logs | 1 year detailed, aggregate afterward |
| Claude raw outputs | retain if used for decisions, otherwise configurable |

Production decision evidence must not be deleted while related trading records are retained.

## 21. Backup and Restore

Minimum backup requirements:

- automated daily backups
- point-in-time recovery where available
- separate backup storage from primary database
- periodic restore test
- documented recovery procedure
- backup encryption

Critical restore goals:

- restore production trading state
- restore order and fill history
- restore strategy versions
- restore audit trail
- restore risk limits and kill switch state

If restore state is uncertain, production trading must remain disabled until reconciliation completes.

## 22. Migration Policy

Database changes must be managed through migrations.

Rules:

- Every schema change must be versioned.
- Migrations must be reversible where practical.
- Production migrations must be reviewed.
- Destructive migrations require explicit approval.
- Migration must not silently delete audit or trading records.
- Data backfills must be logged.

Recommended migration naming:

```text
YYYYMMDDHHMMSS_descriptive_name.sql
```

## 23. Data Quality Rules

Trading-critical data must be validated before storage or before use.

Examples:

- asset must have market and currency
- broker mapping must be verified before execution
- market data must have timestamp and source
- AI analysis must pass schema validation
- risk check must reference exact subject
- order approval must reference risk and money checks
- broker order must reference order approval
- fill must reference broker order

Invalid data should be stored as rejected or quarantined input if useful for debugging, but must not be promoted into trading state.

## 24. Privacy and Secret Handling

The database must not store:

- Toss API secrets
- Naver client secrets
- Claude API keys
- account passwords
- certificate files
- raw authorization headers
- unredacted sensitive request logs

Secrets must be stored in a secret manager or environment-specific secure storage.

Payload logging must redact:

- authorization headers
- access tokens
- refresh tokens
- account identifiers where unnecessary
- personal identifiers

## 25. Read Models and Dashboard Views

The dashboard should not directly reconstruct every view from raw events.

Recommended read models:

- current portfolio summary
- current risk status
- active strategy status
- current kill switch state
- latest AI Health Check
- open alerts
- recent orders
- recent fills
- strategy performance summary
- shadow portfolio leaderboard

These may be implemented as:

- SQL views
- materialized views
- cached read tables
- application-level projections

Production-critical state must still be traceable back to source records.

## 26. Concurrency and Idempotency

The database must help prevent duplicate orders.

Required patterns:

- unique idempotency key for order approval or broker submission where possible
- transaction boundary around order approval creation
- lock or compare-and-set behavior around cash reservation
- no duplicate active broker order for the same approved order
- reconciliation before retrying uncertain broker submissions

Possible implementation tools:

- database transactions
- row-level locks
- unique constraints
- advisory locks for scheduled jobs
- outbox pattern for external side effects

## 27. Outbox Pattern

For production-critical side effects, use an outbox pattern where practical.

Example:

```text
transaction:
  create order approval
  create outbox event OrderApproved

worker:
  reads outbox event
  submits broker order
  records broker response
  marks outbox event processed
```

Benefits:

- safer retries
- audit trail before side effect
- recoverable worker failures
- less risk of lost commands

The final broker submission design is defined in `07_Trading_System.md`.

## 28. Initial Implementation Priority

The initial implementation does not need every table fully optimized.

Priority order:

1. assets and broker mappings
2. portfolios, positions, cash balances
3. strategies and strategy versions
4. signals
5. risk limits and risk checks
6. order intents, money checks, order approvals
7. broker orders and fills

## 29. Open Database Questions

The following questions remain open:

- Should the first version use a single PostgreSQL schema or multiple schemas?
- Which ORM or query builder should be used?
- Should market data be stored in PostgreSQL only, or should a time-series extension be introduced later?
- How much raw Claude output should be stored for audit versus cost and privacy control?
- What exact Toss account identifiers need to be stored, and how should they be redacted?
- Does Toss provide stable fill identifiers for deduplication?
- Should portfolio snapshots be event-derived or periodically materialized?
- What is the expected market data frequency for V1?

## 30. Final Database Statement

The database is not just storage.

It is the system's memory, evidence layer, and safety record.

The database must preserve:

- what the system saw
- what the system decided
- why it decided
- what it approved
- what it sent to the broker
- what the broker returned
- what actually filled
- how the portfolio changed
- how strategies evolved

Without this record, automated trading becomes opaque and unsafe. With this record, the system can be reviewed, tested, improved, and trusted cautiously over time.
