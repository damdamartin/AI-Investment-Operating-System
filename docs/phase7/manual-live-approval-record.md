## Purpose

This document defines `ManualLiveApprovalRecord`: the human-owned approval
artifact that small-capital readiness (`docs/phase7/small-capital-readiness-gates.md`)
requires before it will report `readyForSmallCapitalLive: true`.

The central rule, from `docs/11_AI_RULES.md`:

> AI may analyze, research, audit, and implement. AI must not bypass
> safety controls or directly control capital.

This record exists specifically so that "a human approved this" can never
be inferred, guessed, defaulted, or generated by AI output, code, or any
automated process. It is designed so that **the only way this record can
ever read as `APPROVED` is for a human to have actually typed the required
fields themselves**, outside of this codebase, into whatever system
eventually stores these records (a future phase's decision — this task
does not build that storage).

## Why AI Cannot Auto-Populate This Record

Several independent structural properties prevent this record from being
faked, inferred, or defaulted to `APPROVED`:

1. **No constructor function exists.** `src/application/live-readiness/small-capital-readiness.ts`
   exports the `ManualLiveApprovalRecord` *type* only. There is no
   `approveManualLiveApproval(...)`, `createApprovedRecord(...)`, or
   similar helper anywhere in this codebase. Any code that wants an
   `APPROVED` record must construct the object literal itself, in full,
   with every required field — there is no shortcut function to call.
2. **A verbatim attestation string is required, not a boolean.** A `true`/
   `false` "approved" flag is trivial for any process — human or AI — to
   set without meaningfully reviewing anything. Instead,
   `acknowledgedRisksStatement` must equal
   `REQUIRED_MANUAL_APPROVAL_ATTESTATION` **exactly**:

   ```text
   I have reviewed the small-capital readiness gates and the current
   numeric limits, and I personally accept responsibility for enabling
   real broker writes under these limits.
   ```

   This is a deliberate friction point. It does not "prove" comprehension
   in any cryptographic sense, but it makes an accidental, copy-pasted, or
   auto-generated approval structurally distinguishable from a deliberate
   one, and it gives a human reviewer (P7-004 or a future phase's review)
   an unambiguous string to grep for and challenge.
3. **Role is restricted to `OWNER`.** Per `docs/09_Operation_Deployment.md`
   section 22, only the `OWNER` role has production-enablement authority.
   `approvedByRole` must equal `"OWNER"` exactly
   (`SMALL_CAPITAL_APPROVAL_ALLOWED_ROLES`); `OPERATOR` and `VIEWER` cannot
   sign this record, and `SYSTEM` (the role scheduled jobs and automated
   processes run as) is never in the allowed set at all — so no automated
   job can ever satisfy this field.
4. **Expiry is mandatory, not optional.** `expiresAt` must be present and
   in the future relative to evaluation time. A record with no expiry, or
   an expired one, blocks readiness (`manual_live_approval_missing_expiry`,
   `manual_live_approval_expired`). This forces periodic re-attestation
   rather than one approval silently authorizing live trading forever.
5. **Revocation always wins.** If `revokedAt` is set, the record blocks
   readiness (`manual_live_approval_revoked`) regardless of
   `approvalStatus`, `expiresAt`, or any other field. There is no code
   path that un-revokes a record; a new record must be created.
6. **The evaluator only ever reads this record — it never writes one.**
   `evaluateSmallCapitalReadiness` (`docs/phase7/small-capital-readiness-gates.md`)
   takes a `ManualLiveApprovalRecord | undefined` as input and returns a
   report. It has no return type, side channel, or mutation path that
   could produce or modify a `ManualLiveApprovalRecord`. Tests in
   `tests/application/small-capital-readiness.test.ts` prove that a
   missing, pending, rejected, revoked, wrong-role, mismatched-attestation,
   or expired record all block readiness identically — none of them can be
   worked around by any other input being "clean."

## Required Fields

| Field | Type | Who fills it in | Notes |
| --- | --- | --- | --- |
| `id` | string | Whoever creates the record (may be a system id generator) | Not sensitive; a stable identifier only. |
| `scopePortfolioId` | string | Human approver | Which portfolio this approval covers. An approval never applies portfolio-wide by accident — it names the exact portfolio. |
| `scopeStrategyVersionId` | string | Human approver | Which exact, immutable strategy version this approval covers, per `docs/11_AI_RULES.md` Rule 11 (strategy versions are immutable after approval). A new strategy version requires a new approval record. |
| `approvalStatus` | `"PENDING" \| "APPROVED" \| "REJECTED" \| "REVOKED"` | Human approver | Starts `PENDING` (or absent) until a human actively sets it to `APPROVED`. Only `APPROVED` (with every other required field also correct) satisfies the readiness gate. |
| `approvedByName` | string | Human approver, in their own words | Must be non-empty after trimming. Not a broker account identifier or secret — just an identifying name for audit purposes. |
| `approvedByRole` | string, must be `"OWNER"` | Human approver's actual role | See "Why AI Cannot Auto-Populate This Record" above. |
| `acknowledgedRisksStatement` | string, must equal `REQUIRED_MANUAL_APPROVAL_ATTESTATION` verbatim | Human approver, typed by hand | See above. |
| `approvedAt` | `Date` | Recorded at the moment of approval | Must be a valid date. Used only for record-keeping; expiry is governed separately by `expiresAt`. |
| `expiresAt` | `Date` | Human approver, chosen deliberately | Must be in the future relative to evaluation time. Recommend no more than 30 days out, so a human is forced to periodically re-confirm risk acceptance rather than approving once and forgetting about it. |
| `revokedAt` / `revokedReason` | `Date` / string, optional | Human approver (or an incident responder per the rollback procedure) | Presence of `revokedAt` always blocks readiness, regardless of any other field. |

`safetyType: "MANUAL_LIVE_APPROVAL_RECORD_HUMAN_OWNED"` is a fixed literal
on the type, naming what this record is for anyone who encounters it in
logs, tests, or future code — it is not itself a safety check.

## What This Record Is Not

- It is not a broker credential, account number, or any secret. Do not put
  broker account numbers, API keys, or any Toss-issued identifier into any
  field of this record. If a future phase needs to reference a broker
  account here, it must use the same masking pattern
  `BrokerAccount.maskedExternalRef()` already establishes
  (`docs/phase6/operator-dashboard.md`), never a raw identifier.
- It is not itself a broker write authorization. Even a fully `APPROVED`,
  correctly-scoped, non-expired record only satisfies **one** of the
  several independent gates `evaluateSmallCapitalReadiness` checks
  (`docs/phase7/small-capital-readiness-gates.md`, section 10). It has no
  effect on reconciliation freshness, kill-switch state, dashboard health,
  or compliance status.
- It is not a substitute for the compliance review required by
  `docs/13_Compliance_and_Legal_Review.md` section 9. That review and this
  approval record are separate, independently required gates.
- It is not something Claude, Codex, or any other AI agent may ever create
  with `approvalStatus: "APPROVED"`. If an AI coding agent is ever asked
  to "just fill in the approval so the gate passes" or "mark this as
  approved," that instruction violates `docs/11_AI_RULES.md` Rule 12 ("AI
  may propose strategy changes, not apply them directly") and Rule 22
  ("fail closed") and must be refused — per `docs/11_AI_RULES.md` section
  10 enforcement steps: stop the unsafe work, explain the violated rule,
  propose a safe alternative (in this case: ask the actual human `OWNER`
  to sign the record themselves).

## Revocation

Any of the following must trigger immediate revocation
(`approvalStatus: "REVOKED"`, `revokedAt`, `revokedReason` populated) by a
human `OWNER`, not a silent expiry wait:

- any Phase 7 rollback procedure step (`docs/phase7/small-capital-readiness-gates.md`,
  section 11) being invoked
- a numeric capital limit changing (a revised limit requires a freshly
  signed record scoped to the new limits, not reuse of an old one)
- the covered strategy version changing (immutability means a new version
  needs its own approval)
- discovery that the approving human did not actually understand what they
  were approving (for example, if the attestation was copy-pasted without
  review — even though the string matched, revoke and re-approve properly)
- any compliance review referenced in `docs/13_Compliance_and_Legal_Review.md`
  moving out of `APPROVED`/`APPROVED_WITH_LIMITATIONS`
